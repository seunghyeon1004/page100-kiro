Decisions already made:
- `EditorClient` is an interface with one method, `draft(request) -> Promise<DraftResult>`, where a request carries the page number, the slot limits (rows, width), the source text and, on a retry, the previous draft and its violations. Implementations: `AnthropicEditorClient` (the real one), `FixtureEditorClient` (replays recorded drafts from test/fixtures/editor/, used by tests and by an offline demo mode), and scripted fakes inside tests.
- AnthropicEditorClient uses the official `@anthropic-ai/sdk` (pin the current version from the npm registry), model from `EDITOR_MODEL` (default `claude-opus-5-5`), `client.messages.parse` with a zod output format (`zodOutputFormat` from `@anthropic-ai/sdk/helpers/zod`) so the reply is `{ rows: string[] }`, `output_config: { effort: "low" }`, `max_tokens: 4000`, no `temperature`/`top_p`/`top_k`, no `thinking` parameter, no assistant prefill, a 30 s timeout and `maxRetries: 1`. Check `stop_reason`: `refusal` and `max_tokens` are failed drafts, not errors to retry blindly. Catch SDK errors most-specific first (rate limit, other status errors, connection errors) and never include the key, the headers or the request body in a log line or an error message.
- The system prompt is built from the rules in editorial.md (voice, headline rules, abbreviations, fitting) and states the limits. The source text goes in the user message inside a clearly delimited block and is described as untrusted data: instructions inside it are to be ignored. The model returns plain text rows only.
- Draft checks, each returning exact violation sentences that are sent back on retry: row count and width per slot (measured in code points after folding), repertoire (foldText must succeed), no `{` tags, the numeric fidelity check exactly as editorial.md defines it, no row that is only whitespace inside a paragraph unless the slot allows it. The checks are pure and are the only way a draft becomes "accepted".
- `editPage`: at most three calls per page (first draft plus two retries with the violations). If no draft is accepted, or the client fails, or the budget is exhausted, the result is the rule-based rows. The output always goes through `assemble`, so an accepted draft that assemble rejects is also a rejection.
- `CallBudget`: counts calls per UTC day against `MAX_MODEL_CALLS_PER_DAY` (default 60); the check happens before every call; when the cap is reached no call is made until the next UTC day. In memory only; say plainly in the design that a process restart resets it, and add `EDITOR_MAX_CALLS_PER_BOOT` (default 30) as a second cap that does not reset with the day, so a restart loop cannot spend without bound per process.
- Draft cache: keyed by a SHA-256 of the page number, the limits and the source text. An accepted draft is reused while the key is unchanged, so an unchanged story costs no call. A rejected-three-times key is remembered too, so it is not retried until its text changes.
- `runEdition(snapshot, status, now, deps)`: for the ai pages only (110, 111-118, 500, 501, 700), in page order, one call at a time; returns the CompiledPages with `editor: "ai"` or `"rules"` and updates the counters that page 802 shows (calls today, cap, drafts accepted, drafts rejected, pages on rules fallback).
- With no `ANTHROPIC_API_KEY`, src/editor is never constructed with the real client and makes no call; pages are the rule-based ones.
- scripts/record-editor-fixtures.ts records real drafts for the boot snapshot into test/fixtures/editor/ (input hash, request without the key, response rows, model id, date). Only the owner runs it, with a real key; tests never do. The spec must not ask Kiro to read any .env or secrets file.

**Decisions I made that you didn't specify:**
- **Reply format:** the reply stays `{ rows: string[] }`. Slots come in order, separated by one `""`. A slot may be empty only where the rule-based draft also left it empty, so the editor can fit more items, never fewer.
- **What a call is:** a call means one HTTP request. With `maxRetries: 1`, one draft can make two requests. So the budget reserves 2 before each draft, a counting `fetch` refuses a third, and unused calls are refunded. This keeps both caps hard even when the SDK retries.
- **Stopping and remembering:** a rate-limit, 401 or 403 error stops the whole edition. A refusal stops that page and remembers its input key as rejected. Timeouts and connection errors don't mark the key, so the page is tried again next edition.
- **Voice checks:** I added checks beyond your list because `editorial.md` says the draft checks enforce its rules. They reject `!` or `?`, "breaking/shock/slams", or an all-caps word unless the source has it (allowed abbreviations pass). A headline also can't end in `.` or `...`.
- **Extra pass before accepting:** an accepted draft also goes through `checkCompiledPage` and `buildScreen`, the same checks `compileAll` runs.
- **Work outside `src/editor`:**
  - `src/server/config.ts`, holding only the editor variables.
  - Two new environment variables, `EDITOR_MAX_CALLS_PER_BOOT` and `EDITOR_CLIENT`.
  - Pages 400–402 stay rules-only, which differs from `product.md`.

  All of these are listed under "Departures" in the requirements.
